# 2026-08-08 — Phase 20c: the suites answer for themselves

The map's suite nodes stop being described and start being asked. An inventory
collected by the tools that run the suites, a fold from the reporters' own output
onto the nodes, the workflow wiring that produces both — and one live cycle,
which lit the apply half 20b.2 never reached and broke exactly one thing.

## What this session established

**Reading the repository before writing code killed three lines of the plan.**
`docs/next-phases.md` said the inventory would come from `pytest --collect-only`
and `playwright --list`. None of the three problems below is visible from that
sentence, and all three are visible from the files.

```text
tests/db has no collector    it is a standalone script whose checks were
                             statements inside one function. It was GIVEN
                             --list rather than described from outside
the map's gate has no test   site-data-check runs in terraform-checks, which
dependencies                 installs neither the venvs nor node_modules
the db assertion exists      tests/db/ is the local gate; app/scripts/ is baked
TWICE                        into the image and is the copy stage and prod
                             actually run - the one the map observes
```

The two copies had been asked to mirror each other by a comment at the top of
each file, for eleven phases. That is now a refusal with both lists printed.

**A gate that has only ever been seen green is indistinguishable from one that
cannot fail**, so eleven deliberate defects were used, with a green control
before the first and after the last. The full log is
`2026-08-08-phase-20c-the-suites-answer-for-themselves.log`.

```text
inventory   a renamed test, the two db copies disagreeing, the db check list
            emptied, a pytest suite with its files moved away, a pin the machine
            does not have, a spec answering to a project from outside its
            directory, and the map naming a suite nothing can collect
the fold    every suite called passed, a test the report never mentioned
            silently dropped, an unknown test swallowed instead of named, and
            the cases directory moved away
```

**One break test refused to break the way it was designed to, and that is the
finding.** `collect-suites.py` carries a "refusing to report zero" branch for a
suite that collects nothing. For the pytest suites it is unreachable: pytest
exits 5 first and prints its own `no tests collected`, so the collector-failed
refusal fires instead. Red either way, readable either way — but the stated
reason is now known to hold only for the db suite, and that is written down
rather than left as a comfortable assumption.

**A decision was reversed by looking before pushing.** The collected versions of
pytest and Playwright were written into `site/data/suites.json`, on the argument
that discovery through a tool is a version-dependent fact. `gh pr list` then
showed two open Dependabot PRs, one of them bumping `@playwright/test` — the
exact input. That PR would have gone red on DRIFT saying nothing: same tests,
different string, and the only fix a human commit onto a branch the bot owns, on
every bump, for ever. The comparison stays (a machine whose pytest is not the
pinned one is still refused, by name); the artifact carries no version. **ADR-0042
D3.**

**Two claims of my own were wrong in the same hour, and both were caught by
measuring.** The ADR said collection costs "about 35 seconds in CI" — an estimate
in the voice of a measurement, in a document whose subject is that difference. It
is five seconds, from the run's own timestamps. And `gh run watch -w ci`, printed
as a validation command in `docs/phase-gates.md`, does not exist: `gh run watch`
takes a run id and the `-w` flag belongs to `gh run list`. It was copied this
session and refused immediately, which means it had been written from memory
rather than from a terminal — in the one block of that document that claims to
record what was run.

## Validation

```bash
make suite-inventory-check   # clean on three hosts: sandbox, devbox, runner
make results-check           # 10/10
make test-unit               # 112
make docs-check              # 6 documents, 0 findings
make site-data-check         # 43 ADRs after ADR-0042
gh run watch "$(gh run list -w ci -L 1 --json databaseId --jq '.[0].databaseId')"
```

Every CI run was checked against the step's own OUTPUT, not against its tick:
`9/9 result fixtures fold as expected` and `suite-inventory: clean - 180 tests`
were read out of the job log both times. That habit is what produced the
five-seconds-not-thirty-five correction, and it is the same habit that refused to
let `db: incomplete` stand as a guess.

## The cycle

Apply `31276975666`, 15m51s. Destroy `31277877190`, 9m17s. Both green, every step.

**The apply half of 20b.2 is lit for the first time.** `nodes-apply.json` had
never existed; the map now carries VPC 26s, Secrets Manager 8m25s, RDS 8m24s,
ALB 3m8s, ECS 12s, CloudWatch 1s, Budgets 6s, each with the identifier the
provider handed back. Real results reached the suite nodes: api 52 passed,
regression 12, smoke 2.

**And db came back `incomplete, 1 passed, 1 not_run` for a suite that passed both
its checks.** The first explanation reached for was a race — the task stops
before its last line is delivered — and a stability wait for it was written
before the log was read. The log refuted it in one command: all three events were
there, on ONE line, because `aws logs get-log-events --query 'events[].message'
--output text` joins an array with TABS, and the fold anchors a verdict to the
start of a line.

That is this project's own recurring lesson arriving from a new direction: the
guess was plausible, the fix for it was already written, and the evidence cost
one `grep`. The capture is fixed where it broke (`--output json`, `jq -r` per
message). The wait stays as a precaution and now says in place that it has never
been seen to fire. The real bytes are fixture
`a-flattened-log-capture-is-incomplete`, and what it pins is not the bug — it is
that **the fold named the gap instead of filling it in**, which is why a lying
capture surfaced as `incomplete` rather than as two green checks.

## Three findings for the page, from watching rather than from reading

```text
every node of a running phase says "running now" while terraform creates one.
  The live source is the Actions API and it is anonymous at STEP level; one
  step, `terraform apply`, makes all seven groups. For the SUITES this is not
  true - each has its own step - so per-node live binding is available there
  today, without a new source
a phase that has FINISHED falls back to "nothing recorded yet" until the run
  publishes at the end, which is indistinguishable from never having run. The
  page has two states, at-rest and pulsing, and the run's intermediate truth
  has no representation
suite.db.stage is drawn in the quality gate, and its step runs in Provision.
  prod-gate includes its db step; stage-gate does not. The existing gate checks
  the binding of a PHASE to a step, never of a node
```
